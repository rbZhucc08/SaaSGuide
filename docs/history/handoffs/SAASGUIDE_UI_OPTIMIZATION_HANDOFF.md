# SaaSGuide 页面优化交接文档

> 用途：交给新的 Codex 对话，在不破坏现有业务功能、Agent Workflow、接口和证据边界的前提下，完成 SaaSGuide V2 的 UI/UX 精修。

## 一、给下一对话的最短指令

请进入 `D:\CodexProjects\SaaSGuide`，先完整阅读本文件，再按文末顺序核对当前代码和验收记录。

本轮目标是“基于现有页面做高保真 UI/UX 精修”，不是重新设计业务、重写后端、增加新 Agent，或根据一张效果图重建整个网站。

开始修改前必须先确认 Git 基线、运行现有 107 项测试，并在浏览器中记录当前页面状态。修改后需要重新运行自动测试，并逐页验收空状态、有数据状态、错误状态、ASK、PLAN、人工确认区域和响应式布局。

## 二、需要传递的核心判断

用户提供的参考流程主要是一套“AI 辅助前端设计与开发流程”，作用不只是换颜色，但重点确实是页面视觉、信息层级、组件一致性、响应式和交互反馈。

该流程可以应用到 SaaSGuide，但应当选择性应用：

```text
保留现有功能、路由、API 和 DOM 结构
→ 提取并完善当前设计系统
→ 先为代表页面形成高保真方向
→ 按公共组件和页面逐步优化
→ 覆盖真实业务状态
→ 自动测试和浏览器双重验收
```

不建议采用：

```text
只看一张 AI 效果图
→ 重新生成全部 HTML/CSS/JavaScript
→ 再尝试补回原有业务功能
```

后者很容易得到“外观更漂亮，但 Agent、表单、引用、人工确认和异常状态退化”的样板页面。

## 三、做出判断的可核查依据

以下是判断依据的摘要，不是隐藏推理过程。下一对话应通过仓库文件和浏览器再次核对。

### 1. 当前项目已经不是空白原型

SaaSGuide 已有八项完整导航、七个功能页、一个根工作台和后台学习实验。页面已经共享：

- 深色侧栏；
- 紫色品牌色；
- 浅灰画布；
- 白色圆角卡片；
- 统一按钮、表单、标签和消息样式；
- 980px、820px、700px 等响应式断点。

公共样式位于 `v2-shell.css`。因此当前更需要“设计系统精修和状态统一”，而不是重新从零生成页面。

### 2. 页面承载了真实交互契约

现有页面不是纯展示图，包含：

- XLSX 字段映射、校验、预览和确认；
- 风险扫描和人工判断；
- DeepSeek ASK/PLAN；
- 引用白名单和 Skill trace；
- 文本证据人工核对；
- SQLite 行动创建和状态转换；
- 报告指标和文件导出；
- OCR_REQUIRED、未配置语音和模拟适配器等限制状态。

如果只根据截图重写页面，很容易破坏这些状态、事件监听、DOM ID 或接口数据结构。

### 3. 项目已有可保护的验证基线

- 107 项自动测试通过。
- 七个功能页曾完成统一视觉与主要交互验收。
- 真实 DeepSeek 已验证两次递进 ASK 和最终合法 PLAN。
- 872 CSS 像素宽下，AI PLAN 页面无横向溢出且控制台无 warning/error。
- 历史上 390 × 844 页面曾通过部分响应式检查，但最新 AI 面板尚未做精确 390 × 844 全流程复验。

这些现有证据意味着 UI 优化必须以回归测试为前提，不能只验收静态截图。

### 4. 这是业务工作台，不是营销落地页

项目的核心体验是“清晰、可信、可追溯和可操作”。最重要的视觉目标应是：

- 信息层级；
- 数据密度；
- 表格与表单可读性；
- AI 建议和确定性证据的区分；
- ASK、PLAN、失败、人工确认等状态的区分；
- 长文本和引用的可扫描性；
- 空状态、加载状态和错误反馈；
- 桌面及手机端操作效率。

大量装饰图、粒子、强发光和复杂动画可能削弱可信度，并增加性能和维护成本。

## 四、对参考流程逐项判断

| 参考步骤 | 适用程度 | SaaSGuide 中的正确用法 | 主要风险 |
|---|---:|---|---|
| 生成前端/UI 提示词 | 很适合 | 把视觉方向、组件、间距、状态、响应式和不可破坏项写成 UI Specification | 提示词只写风格、不写业务约束会导致功能遗漏 |
| AI 生成 UI 效果图 | 可以使用 | 先做概览、风险雷达、数据源三个代表页面，确定统一方向 | 效果图不能表达 API、异常、ASK/PLAN 和人工确认逻辑 |
| 拆分页面素材 | 低优先级 | 只有确实需要品牌插图或空状态插图时再做 | 业务工作台不需要大量 PNG 装饰素材 |
| 整理开发提示词 | 很适合 | 明确保留路由、API、DOM ID、字段、状态语义和测试 | 模糊提示会诱导重写全部页面 |
| 分模块开发 | 很适合 | 公共 Shell 和组件先行，再逐页优化 | 多页同时改会让回归定位困难 |
| 对照 UI 不断修正 | 很适合 | 每轮只修具体差异，并同时检查真实交互 | 只追求像图，可能牺牲内容适配和可访问性 |
| 响应式、交互和动画 | 适合 | 加载、折叠、状态转换、移动导航和轻量反馈 | 过度动画影响操作效率和稳定性 |

## 五、当前视觉基线

当前设计变量位于 `v2-shell.css`：

- 画布：`#f5f7fb`
- 卡片：`#ffffff`
- 主文字：`#182035`
- 次文字：`#69738a`
- 品牌紫：`#6557e8`
- 危险红：`#dc3f57`
- 成功绿：`#198865`
- 侧栏：`#202238`
- 侧栏宽度：224px
- 主卡片圆角：14px

这些值可以调整，但应先形成一套完整设计系统，不要在不同页面随意加入新的紫色、灰色、圆角或阴影。

## 六、建议的目标视觉方向

建议定位为：

> 克制、可信、清晰的 AI 项目风险工作台；介于成熟 B2B SaaS 后台与 AI 协作工具之间，而不是炫技型概念页面。

推荐特征：

- 保留深色导航和浅色内容区；
- 提升主标题、页面摘要、核心操作和次要说明的层级；
- 卡片减少无意义边框堆叠，使用稳定的间距和少量阴影；
- 风险等级、系统状态、AI 状态和人工状态使用不同语义色；
- AI PLAN 使用“证据—判断—行动—确认”分区；
- ASK 使用问题清单，不与错误提示混淆；
- Skill trace 默认折叠，但展开后应像运行时间线，而不是普通文字列表；
- 表格与长引用优先可读性和溢出处理；
- 动画仅用于加载、展开、成功/错误反馈和导航，不做持续装饰动画。

## 七、必须冻结的功能边界

UI 优化开始前，把下列内容视为冻结契约。除非发现明确 Bug，否则不要改变。

### 路由

- `/`
- `/data-sources`
- `/risk-radar`
- `/evidence-intake`
- `/knowledge-base`
- `/action-tracker`
- `/reports`
- `/input-lab`
- `/builder`
- 现有 `/api/...` 接口

旧 `/v2` 已有意退役，不要因为做展示页面而恢复。

### 业务语义

- 候选风险不等于正式风险。
- 规则命中不等于 AI 判断。
- AI PLAN 不等于已采用计划。
- 人工确认不等于行动已完成。
- 固定模拟评测不等于真实业务准确率。
- 无模型、无 OCR、无语音、无外部连接器时必须继续显示真实限制。

### Agent 契约

- DeepSeek 信息不足返回 ASK，充分时返回 PLAN。
- PLAN 最多 3 条行动。
- 引用只能来自程序白名单。
- Skill trace 要保留。
- 模型失败时确定性扫描仍可使用。
- AI 不能自动点击人工确认或改变正式状态。

### 前端技术契约

- 不随意重命名现有 DOM ID、表单 `name`、按钮和 JS 查询目标。
- 不改变 API 请求字段和响应字段。
- 不把 `textContent` 渲染改成不安全的模型 HTML 注入。
- 不删除错误、空状态、加载和禁用状态。
- 不将开放文本 XLSX 映射重新改回封闭下拉框。

## 八、建议的实施顺序

### 阶段 0：建立 UI 基线

1. 检查 Git 状态和最新提交。
2. 运行 `run_checks.ps1`。
3. 启动本地服务。
4. 逐页截取当前桌面和手机基线。
5. 记录每页的功能状态、控制台和横向溢出。

没有基线就不能判断优化是否造成退化。

### 阶段 1：设计系统规格

先生成或补充一份 UI Specification，至少包括：

- 色彩 tokens；
- 4px/8px 间距体系；
- 字号、行高和字重；
- 卡片、按钮、表单和标签规格；
- 状态色语义；
- 表格和长文本规则；
- focus、hover、disabled、loading、error；
- 桌面、平板、手机断点；
- 动画时长和减少动画策略。

### 阶段 2：代表页面方向

先选择三个页面：

1. `/`：验证整体 Shell、概览层级和空状态。
2. `/risk-radar`：验证 AI、证据、行动和人工确认的复杂状态。
3. `/data-sources`：验证表单、字段映射、错误和预览。

如果需要 AI 效果图，只为这三个页面建立方向。效果图是参考，不是验收真相。

### 阶段 3：公共组件

优先整理 `v2-shell.css`，建立或统一：

- App Shell；
- Sidebar；
- Page Header；
- Card/Panel；
- Metric Card；
- Button；
- Form Field；
- Status Badge；
- Message/Toast；
- Empty State；
- Table；
- Disclosure/Details。

公共组件稳定后再改页面专属样式，避免每页复制一套规则。

### 阶段 4：逐页优化

建议顺序：

```text
公共 Shell
→ 概览
→ 风险雷达
→ 数据源
→ 文本证据
→ 知识库
→ 行动跟踪
→ 报告
→ 输入实验室
```

每完成一页就做该页浏览器回归，不要等七页全部修改后再集中排错。

### 阶段 5：完整状态覆盖

至少验收：

- 空状态；
- 有数据状态；
- 加载状态；
- 成功提示；
- 表单校验错误；
- API 失败；
- DeepSeek 未配置；
- DeepSeek ASK；
- DeepSeek PLAN；
- 超长风险标题；
- 超长引用；
- 禁用按钮；
- 人工确认区域；
- 展开的 Skill trace。

### 阶段 6：响应式与可访问性

建议至少检查：

- 1440px 桌面；
- 当前约 872px 的应用内浏览器；
- 768px 平板；
- 390 × 844 手机。

检查：

- 是否出现页面级横向滚动；
- 导航是否可达；
- 主操作是否被隐藏；
- 表单和按钮是否过窄；
- 表格如何滚动或转为卡片；
- 长文本是否截断关键信息；
- 键盘 focus 是否清晰；
- 颜色对比是否足够；
- `prefers-reduced-motion` 是否关闭非必要动画。

### 阶段 7：最终回归和证据

1. 运行全部 Python 测试。
2. 运行数据校验和所有页面 JS 语法检查。
3. 逐页检查控制台。
4. 检查请求是否仍返回原有状态。
5. 真实验证风险扫描、ASK/PLAN 和 Skill trace。
6. 不点击会制造无意义正式数据的按钮，除非为测试使用隔离数据。
7. 新增 UI 验收记录，明确已检查和未检查内容。
8. 完成 Git 提交。

## 九、优先优化的页面问题

### 1. 风险雷达

这是最高优先级，因为它最能展示 AI 项目能力。

建议重点：

- 把规则证据、AI 研判、行动草稿和人工判断分成清晰层级；
- ASK 与 PLAN 使用不同布局，而不只是不同文字；
- 引用默认摘要显示，支持展开详情；
- Skill trace 改为紧凑时间线或步骤状态；
- 用户补充信息输入框不要与人工决策说明共用模糊视觉；
- 明确区分“调用 AI”和“确认风险”的按钮层级。

### 2. 数据源

建议重点：

- 上传、字段映射、校验、预览、确认形成清晰步骤；
- 保持字段映射为开放文本输入和表头建议；
- 错误应定位到字段与原始列；
- 映射区域在手机端避免横向拥挤；
- 用户修改过的映射和值要保持可见。

### 3. 根工作台

建议重点：

- 没有导入数据时提供明确但克制的下一步；
- 关键指标不要在无数据时制造“看似有结果”的固定样板；
- 最近活动、行动和数据来源按重要性排列；
- 不放阶段验收、开发说明和 HR 演示文字。

### 4. 知识库和报告

建议重点：

- 引用版本、生效状态和拒答原因更易扫描；
- 报告数字与趋势视觉统一；
- 不把确定性检索标为向量 RAG；
- 不把 Python 报告草稿标成 AI 生成。

## 十、素材与图片策略

当前不建议先拆分或生成大量 PNG 素材。

可能适合使用图片的地方只有：

- 首页空状态的一张克制插图；
- HR 演示文档中的架构示意图；
- 项目 README 的界面截图；
- 作品集封面图。

导航图标、状态图标和装饰线条优先使用现有代码、CSS 或统一 SVG 图标，不要为简单图标生成位图。

若使用 AI 效果图：

- 它只用于确认视觉方向；
- 不直接作为网页背景；
- 不以像素级还原为唯一目标；
- 必须补齐效果图没有展示的错误、加载、空状态和人工确认状态。

## 十一、动画策略

推荐：

- 150–220ms 的按钮和卡片状态变化；
- 轻量的展开/折叠；
- AI 运行步骤的非循环进度反馈；
- 成功和错误消息的短时进入效果；
- 手机导航展开。

不推荐：

- 持续漂浮；
- 大面积粒子；
- 强烈发光；
- 自动轮播；
- 阻塞操作的长入场动画；
- 让指标数字不断跳动的装饰动画。

动画不应成为“AI 能力”的替代品。

## 十二、主要风险、成本和容易忽略的变量

### 功能回归风险

统一组件时可能改掉 ID、选择器、事件绑定或表单行为。必须通过自动测试和真实交互确认。

### 静态效果图偏差

效果图通常只展示理想成功状态，不包含错误、空状态、长文本、禁用和人工审批。实现时必须主动补齐。

### 内容密度

桌面上看起来宽松的设计，在 872px 或 390px 下可能产生大量滚动或隐藏关键操作。

### 浏览器差异

当前主要证据来自应用内 Chromium 和历史 Chrome 检查；Edge、Safari、macOS、Linux 尚未验证。

### 字体和中文排版

中文行高、英文 ID、代码字段和数字混排会影响卡片高度。不能只用英文效果图判断。

### 可访问性

视觉优化不能移除 label、ARIA、键盘 focus、状态提示和足够的颜色对比。

### 性能和维护

大量图片、动画和第三方 UI 库可能增加加载和维护成本。当前原生 HTML/CSS/JavaScript 架构应优先增量优化。

### 证据边界

页面变漂亮不会增加新的 Agent、RAG、OCR、语音、真实企业集成或商业成果。简历只能把它描述为 UI/UX 和作品集展示质量提升。

## 十三、验收标准

UI 优化完成必须同时满足：

### 视觉

- 所有功能页使用同一设计语言；
- 页面层级清晰；
- 主要操作明显但不抢夺内容；
- ASK、PLAN、错误和人工确认可一眼区分；
- 没有无意义开发说明或阶段验收内容混入产品页面。

### 功能

- 所有路由和 API 继续可用；
- 107 项基线测试继续通过，新增 UI 逻辑应增加对应测试；
- XLSX 开放映射仍可输入自定义原始字段；
- 风险扫描仍产生同样的确定性候选；
- DeepSeek ASK/PLAN、引用白名单、最多 3 条行动和 Skill trace 不变；
- 人工确认仍独立，AI 不自动保存正式结果。

### 浏览器

- 桌面、872px、768px 和 390 × 844 无页面级横向溢出；
- 控制台无 warning/error；
- 主操作在手机端仍可达；
- 超长中文内容和引用不会破坏布局；
- 加载、错误、空状态和禁用状态均已查看。

### 记录

- 新增一份真实 UI 验收记录；
- 明确记录未覆盖的浏览器或状态；
- 保存改动前后截图；
- Git 提交不包含 `generated/`、密钥、个人简历或临时文件。
