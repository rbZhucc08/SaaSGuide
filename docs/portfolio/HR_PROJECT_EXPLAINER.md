# SaaSGuide HR 项目讲解稿

这份文档用于帮助项目所有者理解并介绍 SaaSGuide。它不是要求逐字背诵的宣传稿，也不能替代你亲自操作项目。

## 一句话介绍

SaaSGuide 是一个本地运行的项目风险管理 AI 应用 Demo：程序先从项目任务中发现候选风险，DeepSeek 再根据当前公司制度提出追问或行动草稿，最后由人确认并形成行动记录。

## 30 秒版本

> 我做这个项目，是想验证大模型怎样进入一个可控的业务流程，而不只是做聊天页面。系统先接收项目和任务数据，用确定性规则找出逾期、低进度或阻塞候选；需要语言判断时，再由 DeepSeek 根据当前制度返回 ASK 或 PLAN。模型输出还要经过 Python 的结构和引用校验，最终由人确认。项目使用模拟公司数据，本地运行，没有真实客户和生产部署。

## 两分钟版本

可以按“问题—设计—结果—限制”讲。

### 1. 问题

项目数据常常散落在表格、周报和制度文档里。如果直接把所有内容交给大模型，会遇到事实不清、引用失效和模型越权的问题。

### 2. 设计

我把流程拆成四层：

1. 数据层负责字段映射、校验和来源保留；
2. Python 规则负责逾期、低进度和阻塞等可计算事实；
3. DeepSeek 负责信息是否充分、行动草稿和制度引用；
4. 人工确认负责最终业务判断。

### 3. 结果

当前项目支持 6 家差异化模拟公司、30 个项目、180 条任务和 48 个制度版本；能够完成数据接入、风险扫描、AI 研判、人工决策、行动审计和报告导出。217 项自动测试通过，关键模块语句覆盖率为 89.04%，并保留了分阶段验收记录。

### 4. 限制

数据和标准答案由作者构造，固定评测只能用于回归；项目没有真实客户、多用户权限、公开部署、向量 RAG 或多 Agent。DeepSeek 是 API 调用，不是我训练或微调的模型。

## 页面演示时每页说什么

| 页面 | 展示重点 | 一句话说明 |
|---|---|---|
| 首页 | 真实空状态或已确认记录 | 固定样本不会伪装成用户运行结果 |
| 数据源 | 公司画像、项目、制度、XLSX 映射 | 输入先结构化并保留来源，模型不直接处理混乱表格 |
| 风险雷达 | 候选、规则证据、AI 研判 | 程序先找候选，DeepSeek 再做受控语言判断 |
| 文本证据 | 文件位置和人工核对 | 提取结果必须保留来源并由人核对 |
| 知识库 | 当前生效制度和引用 | 系统限制模型只能引用本次允许的制度 |
| 行动跟踪 | 人工确认、状态和事件 | AI 草稿不能直接进入正式行动 |
| 报告 | 指标、CSV、XLSX | 报告来自确认记录，不用固定样板冒充运行数据 |
| 输入实验室 | PDF/WAV 边界 | 能识别接入边界，但没有把元数据检查说成 OCR 或语音识别 |
| 业务验证 | 外部证据状态 | 研究工具已准备，但真实参与者仍为 0 |

## 关键概念的通俗解释

### DeepSeek API

项目把整理好的上下文通过接口发送给已经训练好的 DeepSeek，再接收结果。项目没有训练 DeepSeek。

### Orchestrator

它是 Python 写的流程协调器，决定先扫描什么、读取哪些制度、何时调用模型、怎样检查结果。可以把它理解成受规则约束的调度员。

### Skill

这里的 Skill 是一个业务步骤的输入、输出和停止条件，不是五个独立机器人。当前定义了数据接入、风险扫描、有依据的评估、行动规划和周报五类步骤。

### ASK

信息不足时不急着下结论，而是返回需要补充的问题。

### PLAN

信息充分后生成的行动草稿。它必须有依据、负责人角色、完成信号和合法制度引用，但仍需人工确认。

### RAG

当前项目有版本化制度检索和引用约束，但不是向量数据库 RAG。介绍时应说“确定性知识检索”，不要说“已经搭建企业 RAG 平台”。

### 多公司与多租户

六家公司是不同模拟上下文，用于验证数据和规则差异。系统没有账号权限和并发隔离，因此不是生产多租户。

### Precision 和 Recall

- Precision 表示规则命中的候选中，有多少符合固定标准答案；
- Recall 表示固定标准答案中的风险，有多少被规则找到。

当前 96.75% 和 86.86% 只属于作者构造的合成回归集，不是 DeepSeek 或真实企业准确率。

## 为什么这样设计

### 为什么不把所有判断交给 DeepSeek

日期、进度和直接依赖可以明确计算。用 Python 处理更稳定、便宜、可解释，也更容易测试。模型只处理需要语言理解和上下文组织的部分。

### 为什么模型不能自动落库

格式正确不代表业务判断正确。高影响动作需要人确认，系统必须保留谁做了决定以及发生过什么变化。

### 为什么需要模拟多公司

只增加同一种任务数量会造成虚假的丰富度。不同公司拥有不同流程、阈值、制度和风险分布，更适合检查上下文切换和规则边界。

### 为什么保留误报和漏报

评测不是为了得到漂亮数字，而是让规则缺口可见。当前 4 个误报暴露规则没有考虑剩余工时，18 个漏报暴露规则只检查直接依赖。

## HR 可能追问的问题

### “这个项目是你训练的模型吗？”

> 不是。DeepSeek 是已经训练好的模型，我做的是数据结构、业务规则、上下文准备、调用编排、输出校验、人工确认和评测流程。

### “为什么这算 AI 项目，不是普通网页？”

> 网页只是交互层。AI 位于候选风险研判环节，需要判断信息是否充分，并根据制度生成 ASK 或 PLAN；模型前后都有程序约束，真实调用也有验收记录。

### “你用了几个 Agent？”

> 当前是一个自定义 Python Orchestrator，不是多 Agent，也没有使用 LangChain、LangGraph 或 OpenAI Agents SDK。五个 Skill 是领域步骤合约。因为当前流程是线性的，拆成多个自治 Agent 会增加状态同步、费用和调试成本。

### “96.75% 是模型准确率吗？”

> 不是。这是确定性规则在作者构造的 30 个模拟项目标准答案上的 Precision。DeepSeek 没有完成这 30 个项目的批量评测。

### “项目有什么业务价值？”

> 它展示了一种把数据校验、确定性规则、模型判断和人工审批组合起来的方法。因为没有真实企业采用数据，我不会声称已经产生商业收益。

### “最大的不足是什么？”

> 当前评测数据和标准答案同源，外部标注仍为 0/2；飞书只以作者自建演示数据完成单租户真实链路验收，业务试点参与者为 0，同时没有生产权限、多人协作和公开部署。

### “你具体做了什么？”

如果项目是在 Codex 协助下完成，应诚实表述：

> 我定义了业务目标、流程边界、页面需求和验收方向，并持续根据结果纠偏，例如删除固定样板入口、改成开放字段映射、重做差异化公司数据、恢复 DeepSeek 调用并补充评测。Codex 协助实现代码、文档和测试；我负责需求判断、验证反馈和最终取舍。

不要把 AI 生成的每行代码都描述为自己手写。你真正应该能够说明的是需求、取舍、验证和边界。

## 可以用于简历的事实基础

- 设计并迭代本地项目风险管理 AI 应用 Demo；
- 组织数据校验、确定性规则、模型调用、引用约束和人工确认流程；
- 设计 6 家差异化模拟公司和 30 个项目的固定规则评测场景；
- 为模型输出建立 JSON 结构、引用白名单和行动字段校验；
- 用自动测试和阶段验收记录区分实现、运行和未验证内容。

最终简历措辞还要结合目标职位，不能把这些事实扩写成真实企业经验或商业成果。

## 不要这样说

- “训练了 DeepSeek”；
- “做了企业级多 Agent”；
- “模型准确率达到 96.75%”；
- “已经接入六家企业”；
- “完成了企业 RAG、OCR 或语音识别”；
- “项目已经上线并产生业务效果”。
