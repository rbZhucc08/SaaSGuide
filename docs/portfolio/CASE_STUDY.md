# 项目案例：SaaSGuide 是怎么变成现在这样的

## 起点

SaaSGuide 最初只是一个固定风险看板，用来练习前端交互和大模型结构化输出。页面能展示风险，也能调用 DeepSeek，但数据、场景和流程都比较固定。

继续扩展功能之前，项目暴露出两个问题：

1. 固定页面只能证明页面可以显示，不能证明它能处理新的项目数据；
2. 把更多模拟任务堆进同一家公司，只会增加数量，不会增加业务差异。

因此 V2 的重点从“再做几个页面”改成“建立可以解释和验证的数据链路”。

## 第一次关键调整：先整理数据，再谈 AI

V2 增加了 XLSX 字段映射、标准化 JSON 和来源行号。用户可以使用自己的原始列名，程序负责建议映射和拦截不存在的列。

这一步解决的不是模型能力，而是输入可靠性：如果日期、依赖或任务编号都不可信，后面的 AI 结论没有意义。

## 第二次关键调整：规则和模型分工

逾期、临期、阻塞和直接依赖可以用 Python 明确计算，不需要让模型猜。确定性规则先生成候选风险，并保留命中的字段和规则。

DeepSeek 放在规则之后，负责两件更适合语言模型的事：

- 判断现有信息是否足够，不足时返回 ASK；
- 结合当前制度，把候选整理成有引用的行动草稿。

这样做让每一层的责任更清楚：程序负责可计算事实，模型负责受控语言判断，人负责最终决定。

## 第三次关键调整：不把模型输出直接写入正式记录

模型输出会经过 Python 校验。引用必须来自本次允许的制度列表，行动不能超过三条，步骤必须连续，还必须包含负责人角色和完成信号。

即使通过校验，PLAN 仍然只是草稿。用户还要单独确认风险结论和行动。这个设计避免“结构正确”被误认为“业务结论正确”。

## 第四次关键调整：从同质数据改成差异化公司

早期模拟数据虽然数量增加，但多个场景的结构相似。后来数据重新设计为六家公司：企业软件、跨境电商、制造、物流、营销服务和医疗信息化。

每家公司有独立的：

- 业务背景和经营特征；
- 项目和任务名称；
- 逾期阈值和临期窗口；
- 升级角色和必备证据；
- 制度版本。

这些数据不是用来训练 DeepSeek，而是让规则和模型拥有更具体的公司上下文。

## 第五次关键调整：给规则建立标准答案

数据变多不等于验证变好。为此项目增加了 30 个固定项目标准答案，并故意保留两类边界：

- 小工时但临期低进度，观察规则是否产生误报；
- 间接依赖被阻塞，观察只检查直接依赖的规则是否漏报。

固定结果为 TP=119、FP=4、FN=18、Precision=96.75%、Recall=86.86%。这组结果的作用是暴露工程缺口和防止回归，不是宣传真实准确率。

## 现在的系统

```mermaid
flowchart LR
    A[用户数据或模拟项目] --> B[校验与来源保留]
    B --> C[规则候选]
    C --> D[当前制度]
    D --> E[DeepSeek ASK / PLAN]
    E --> F[程序校验]
    F --> G[人工决定]
    G --> H[行动、审计和报告]
```

项目现在能够演示：

- 如何把非结构化或表格数据变成可追踪输入；
- 如何组合确定性规则、知识检索和模型；
- 如何限制引用和模型输出结构；
- 如何在人机流程中保留人工确认；
- 如何用固定评测发现误报和漏报；
- 如何诚实记录未实现和未验证内容。

## 结果证明了什么

可以证明：

- 当前代码在本地可以运行；
- 约定的输入、规则、模型校验、人工确认和报告链路已经实现；
- 当前固定测试和模拟场景可复现；
- 真实 DeepSeek 在验收输入上返回过合法 ASK 和 PLAN。

不能证明：

- 系统在真实企业数据上具有同样准确率；
- DeepSeek 可以替代项目负责人；
- 项目已经产生商业价值；
- 当前本地架构可以直接用于生产环境。

## 如果继续发展

最有价值的下一步不是增加更多固定页面，而是找一组与生成器独立的人工标注数据，或者接入一个经过授权和去标识化的真实业务子流程。那时才能开始讨论外部有效性，而不只是工程回归。
